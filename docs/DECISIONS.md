- **2026-05-31 · EPIC-A: one canonical date→puzzle policy for every producer + cron-failure monitoring.** The daily puzzle had *four* producers that each derived "today's puzzle" differently, so the same date could yield different puzzles depending on which ran: the CLI seeder (`scripts/seed-puzzles.ts`) used its own FNV `dateSeed` + an `easy/medium/hard/medium` cadence; a second web seeder (`apps/web/scripts/seed-puzzles.mts`) used `hashSeed(date)` + always `medium`; the edge function used **`Math.random()`** + always `medium`; the `/play` offline fallback used `generatePuzzle()` with **no seed** (a fresh random puzzle every request) and no `puzzleId`. The cron was fire-and-forget — a minting failure surfaced to nobody and silently dropped users onto the unrecordable fallback (broken streaks, unseen). *Fix:* (1) New `packages/engine/src/daily.ts` is the single source of truth — `dailyPolicy(date)` returns the canonical FNV seed + cadence difficulty (Euclidean-mod so pre-epoch dates stay in range; epoch 2026-01-01 = day 1), and `generateDaily(date)` generates from it, **retrying on a fresh date-derived deterministic seed** (`date#1`, `date#2`, …) before throwing, and reports the `usedSeed` that succeeded so the stored row reproduces exactly. 12 unit tests (`daily.test.ts`) cover determinism, the cadence, a DST-proof UTC day index, reproducibility, and that the output is rule-valid + uniquely + deduction-solvable. (2) **All** producers now call it: the CLI seeder, the edge function (`daily-puzzle/index.ts` — no more `Math.random`; re-vendored into the Deno engine via `sync-engine.sh`), and the `/play` fallback (`generateDaily(today).puzzle` — the canonical puzzle for the date, not a random one). (3) The redundant `apps/web/scripts/seed-puzzles.mts` (+ its `seed` npm script) was **deleted** — this also removes the two unexplained `as any` casts (CQ-5). (4) `/play` now distinguishes a genuinely-absent row (cron/seeder failed → `console.error` loudly; solves can't record) from a DB outage, instead of silently degrading. (5) **Monitoring (BE-2):** migration `20260531040000_monitor_daily_puzzle.sql` re-schedules the 00:05 cron to persist its pg_net request id into `daily_puzzle_cron_run`, and adds a 00:15 `check_daily_puzzle()` job that writes to a new `public.ops_alert` table + `RAISE WARNING` when today's `puzzles` row is missing or the call returned non-2xx. Resolves ENG-1, ENG-3, CQ-1, CQ-3, CQ-5, BE-2, and BE-5 (the edge function now follows the difficulty cadence rather than hardcoding `medium`). *Shipped 2026-05-31 (with sign-off):* edge function deployed (`supabase functions deploy daily-puzzle`, re-vendored engine uploaded) — POST returns `200 {ok,skipped}` and `dailyPolicy('2026-05-31')` reproduces the exact seed/difficulty already in prod, so it's consistent with seeded data through 2026-12-31; monitor migration applied (`supabase db push`) and `check_daily_puzzle()` verified clean (HTTP 204, `ops_alert` empty); `main` pushed. *Scope boundary:* **SEC-2** (the edge fn is `verify_jwt=false` with no rate limit) is orthogonal to seed/monitoring consolidation and stays open under Security. *Residual (→ AUDIT BE-6):* the monitor's alerting is **passive** — it writes to `ops_alert` + `RAISE WARNING` (logs) but pushes to nobody; a delivery hook (DB webhook on `ops_alert` inserts → email/Slack, or a scheduled digest) is still needed for a missed mint to actually page someone. *Supersedes* the two stale claims below (2026-05-31 edge-function "explicit random seed"; 2026-05-29 archive "`scripts/seed-puzzles.ts` … medium-difficulty … `hashSeed`").
- **2026-05-31 · EPIC-B: the daily puzzle is served/gated by the same local-day clock as streaks (one canonical clock).** Follow-up to the `local_date`/`tz_date` streak fix: streaks already bucketed by the user's local day, but the *puzzle producers/consumers* still keyed on UTC midnight (`new Date().toISOString().slice(0,10)`), so a UTC+ user near midnight was served the *previous* puzzle while their streak "today" had already advanced — they'd play the N−1 puzzle for an N-day streak, and solves could land on a day with no matching served puzzle. - **2026-05-31 · Dev-only `/api/dev-login` route for verifying authenticated screens (hardened).** Verifying logged-in UI (the account avatar, Stats, win/streak states) previously required a real sign-in, which the agent can't do (typing passwords / creating accounts are disallowed). Added a helper route ([apps/web/src/app/api/dev-login/route.ts](apps/web/src/app/api/dev-login/route.ts)): admin `generate_link` returns a magic-link OTP hash directly (no email sent) → the public `/verify` endpoint exchanges it for a session (non-PKCE path, so no client code-verifier needed) → `setSession` on an `@supabase/ssr` server client writes the auth cookies → 303 redirect home. *Why this shape:* the app's PKCE callback in `proxy.ts` needs a client-initiated verifier that an admin-minted link doesn't have, so `verifyOtp` on a default (PKCE) ssr client fails with "invalid or expired"; the REST `generate_link`→`/verify` flow sidesteps PKCE entirely. *Defence in depth* (a credential-less login endpoint is a classic backdoor pattern, so it has three independent gates, all of which must pass or it 404s without revealing it exists): (1) `NODE_ENV === "development"` — inert in any Vercel/production build; (2) request host must be localhost — not reachable if the dev server is exposed via LAN/tunnel; (3) `?secret=` must equal `DEV_LOGIN_SECRET` (per-machine, set in gitignored `.env.local`; if unset the route is disabled). It's a `POST` (state change shouldn't be a `GET`), only ever authenticates as the single hard-coded throwaway test account `stayrightdemo@gmail.com`, reads `SUPABASE_SERVICE_ROLE_KEY` server-side only, and hard-codes no secrets — safe to commit. **Operational rule:** `SUPABASE_SERVICE_ROLE_KEY` (bypasses all RLS) must NEVER be set in the deployed web environment — this route is its only web-tier consumer and 404s in production, so the deployed app has no need for it. `.env.local.example` documents this.

- **2026-05-31 · Server-side solve validation (H1 audit finding).** Previously any authenticated user could POST a `solves` row for any `puzzle_id` with any `duration_ms` — the RLS only enforced ownership, not correctness. New server action `app/actions/record-solve.ts`: loads `grid_spec` from the DB server-side, parses and validates it via `parseGridSpec()`, checks that every cell in the submitted grid matches `spec.solution[r][c]`, then inserts. A grid mismatch returns `{ ok: false }` without writing. Input is sanitised (puzzleId string, durationMs positive integer, localDate YYYY-MM-DD). Auth is checked via the server-side session — `user_id` comes from the cookie, not the request body, so cross-user inserts are structurally impossible. `BoardScreen` now calls the action instead of the browser client `insert()`; the final grid is captured via `cellsRef` (kept current on every render) so the effect closure is never stale. Streak fetch remains client-side (read-only). *Residual:* the `solution` is still in the world-readable `grid_spec` column, so a determined actor can read it and submit the matching grid. Removing it requires splitting it out of `grid_spec` behind a separate RLS policy — deferred.
